# 实现到位上报与取餐等待推进

## Goal

屏幕仓位任务每到达一个点位后，向上游上报点位名称和仓位号，并在原地等待取餐完成通知。收到通知或等待五分钟后，中间点继续下一点，最后一点调用现有召回能力。

## What I already know

- 机器人 App 固定运行在 `192.168.112.89`。
- 现有 App HTTP 服务监听 `9095`，必须保留现有接口和行为。
- 到位后 App 主动调用 `POST http://192.168.112.194:9088/nav_arrive`。
- 到位请求体为 `{"point_name":"<点位名称>","bay":<1|2|3>}`。
- 上游通过 `POST http://192.168.112.89:9088/pickup_status` 通知取餐完成。
- pickup 请求体保持 `{"pickup_status":true}`，不增加仓位号或任务 ID。
- 屏幕路线按仓位绑定先后生成，不按仓位编号排序。
- 现有召回通过 `ws://192.168.112.194:9098` 发送，不改召回协议。

## Assumptions

- `/nav_arrive` 的响应内容不参与导航决策，导航决策以 `/pickup_status` 回调和本地五分钟倒计时为准。
- 因 pickup 回调不携带任务标识，只在当前有效等待阶段消费一次 `pickup_status: true`。
- 本轮只对屏幕仓位任务启用逐点等待；现有上游 `/robot_task/send_point` 保持原导航语义，并在到达等待期间可抢占旧任务。

## Decisions

- 保留 `9095` HTTP 服务，新增独立的 `9088` pickup 接收服务。
- 到位 HTTP 请求异步发送，不阻塞导航监听线程和主线程。
- 每次开始新等待时生成新的等待代次；超时回调和 pickup 回调必须只作用于当前代次。
- 屏幕仓位路线复用机器人核心初始化时创建的 SDK 导航实例，并将完整路线一次性交给 SDK；每个点到达后暂停，pickup 或超时后通过 `pilotNext()` 继续。
- 当前预期点位只有先进入 `STATE_RUNNING` 后才接受 `STATE_DESTINATION`，并保留任务和 SDK 会话代次校验。
- 路线准备十秒内没有完成时取消任务、恢复“立即出发”和点位编辑，并提示重试。
- 有效 pickup 或五分钟超时都结束当前等待。
- 当前点不是最后一点时，结束等待后调用现有下一点流程。
- 当前点是最后一点时，结束等待后调用现有召回能力。
- 收到有效 `/robot_task/send_point`、停止任务或 Activity 销毁时，取消当前等待和旧超时回调。
- 上游 `/robot_task/send_point` 在抢占前完成 JSON、非空路线和非空节点校验；有效路线仍按完整路线交给 SDK。
- 不修改 pickup 协议，不增加 `bay`、`point_name` 或任务 ID。

## Requirements

- 屏幕仓位任务到达每个点位后，按点位 ID 找到绑定仓位号。
- 到位后向 `/nav_arrive` 发送正确的点位名称和仓位号。
- 到位后机器人保持停止状态并开始五分钟等待。
- `pickup_status` 仅接受 POST JSON，并仅在 `pickup_status` 为布尔 `true` 时推进当前等待。
- 未处于等待状态、重复回调、无效 JSON、缺失字段或非 `true` 值不得推进路线。
- 中间点收到有效 pickup 时立即前往下一点；五分钟超时也前往下一点。
- 最后一点收到有效 pickup 时立即召回；五分钟超时也召回。
- 有效新 `/robot_task/send_point` 抢占时取消旧等待，旧回调不得推进旧路线。
- 保留现有回充、巡仓、召回、地图、仓位绑定和 `9095` HTTP 接口。

## Delivery Progress UI Extension

- 左栏提供“点位选择”和“配送进度”切换，不占用中间地图或右侧操作区。
- 成功创建屏幕仓位任务后自动显示配送进度，并使用出发时的点位、仓位和顺序快照。
- 每个点位显示等待配送、正在前往、等待取餐、已完成取餐、等待超时或配送已取消状态。
- 当前等待点显示五分钟剩余倒计时；pickup 与超时继续复用既有的一次性等待完成路径。
- 屏幕仓位任务期间点位和仓位绑定只读，但允许手动切换两个左栏页面查看信息。
- 最终 pickup/超时结果以及召回或取消状态保持显示，直到下一次屏幕仓位任务替换快照。

## Definition of Done

- 完成到位上报、pickup 接收、五分钟等待和路线推进。
- 更新通信和导航流程文档。
- 完成静态检查、补丁检查和 Debug 构建。
- 在 `progress.md` 末尾追加验证证据、改动文件和回滚点。

## Out of Scope

- 不修改上游 pickup 协议。
- 不为 pickup 回调增加鉴权、仓位号或任务 ID。
- 不持久化等待状态，App 重启后不恢复等待。
- 不改变上游 `/robot_task/send_point` 的请求格式。
- 不改变现有 WebSocket 召回负载。
- 本轮不发布版本、不提交代码，除非用户另行要求。

## Technical Notes

- 主要涉及 `MainActivity` 的导航到位状态、任务抢占和生命周期。
- 上游路线和屏幕仓位路线都复用核心初始化后的 SDK 导航实例；屏幕路线通过任务代次、当前会话代次、预期位置和 `STATE_RUNNING` 门控隔离无效回调，并继续复用 `sendRecallTask()`。
- 应避免复用旧的 20 秒单点返回定时器，防止旧 Runnable 覆盖新任务。
- 新 HTTP 服务应保持入口校验集中，不把路由解析散落到导航代码。
