# 巡仓到点后等待下一条路线超时返回

仅适用于从主界面点击“巡仓”启动的任务。上游通过机器人本机 `9095/robot_task/send_point` 下发路线；每次路线走到末点，App 仍通过 `9096` 上报 `send_point已完成`。状态 WebSocket 连接失败时会按现有逻辑尝试重连。

- 若末点不是出餐口（机器人地图点位 ID `2`），App 从到点起等待 60 秒；收到下一条**有效** `send_point` 就取消本次计时，正常执行新的路线。无效请求不重置计时。
- 若 60 秒内未收到下一条有效路线，App 不调用上游 `9098` 的召回接口，而是用本地 PeanutNavigation 导航至点位 ID `2`。这只是发起返程，能否到达仍以 SDK 回调和真机运行结果为准。
- 若当前路线的末点已是 ID `2`，不再发起返程。手动送餐、回充、召回、上游停止/回充、导航错误或 App 销毁会取消等待，防止旧计时器抢占新任务。
- 普通屏幕送餐和非本机巡仓按钮启动的上游路线不启用此兜底；原有屏幕送餐的五分钟取餐等待保持不变。

上游 `send_point` 协议没有巡仓任务 ID，App 只能用本机“巡仓”按钮启动作为任务标识：在这个标识有效期间，随后收到的有效 `send_point` 都会视为巡仓下一条路线。`9096` 是否已连上不等于上游已经下发下一点；触发兜底的依据是**到点后一分钟仍未收到下一条有效路线**，而不是任一单独端口的连接状态。

真机验收：点击巡仓并让机器人抵达非 ID `2` 的点，分别验证一分钟内下发下一条路线、上游断连且不下发下一条路线、到达点 ID `2`、等待期间手动召回和上游停止。可在“设置 → 运行日志”查看 `WAREHOUSE` 的等待、取消和本地返程记录，结合 `NAV` 的路线准备及 SDK 状态确认机器人是否实际出发。
