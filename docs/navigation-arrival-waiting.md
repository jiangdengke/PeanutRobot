# 导航到位上报与取餐等待

## 适用范围

到位等待只应用于主界面完成仓位绑定后点击“立即出发”的屏幕任务。上游通过现有 `/robot_task/send_point` 下发的路线保持原导航行为，不强制进入仓位等待。

## 到位上报

机器人到达屏幕任务中的每个点位后，App 保持停止状态，并异步请求：

```http
POST http://192.168.112.194:9088/nav_arrive
Content-Type: application/json

{
  "point_name": "餐厅左下",
  "bay": 1
}
```

- `point_name` 来自当前导航点位名称。
- `bay` 来自出发时的仓位绑定快照，只会发送 `1`、`2` 或 `3`。
- HTTP 响应只用于联调日志，不直接决定路线是否继续。
- 请求失败不会提前推进路线，也不会取消本地五分钟等待。

## 取餐完成入口

App 在机器人固定地址 `192.168.112.89:9088` 提供：

```http
POST /pickup_status
Content-Type: application/json

{
  "pickup_status": true
}
```

该端口使用独立的 HTTP 服务，不改变原有 `9095` 服务和 `/robot_task/*` 接口。

只有合法 JSON、布尔值 `pickup_status: true`，并且当前确实处于到点等待阶段时才会被接受。错误方法、错误路径、缺失字段、字符串类型、`false`、重复回调或非等待阶段请求都不会推进导航，并返回对应的 JSON 错误结果。

## 五分钟等待与路线推进

1. 每个点到位后，上报 `/nav_arrive` 并开始五分钟等待。
2. 中间点在五分钟内收到有效 pickup 时立即前往下一点；未收到时在五分钟超时后前往下一点。
3. 最后一个点在五分钟内收到有效 pickup 时立即调用现有 `9098` 召回；未收到时在五分钟超时后调用召回。
4. 同一等待阶段只能被 pickup 或超时消费一次，重复到位事件和竞态回调不会重复推进。

## 导航事件隔离

- 屏幕仓位路线按点位拆成独立导航腿，每一腿创建新的 SDK 导航会话。
- SDK 回调携带对应会话代次，App 只处理当前任务、当前会话的事件。
- 当前导航腿必须先收到 `STATE_RUNNING` 才会接受 `STATE_DESTINATION`，旧任务或上一点迟到的到达事件不会提前上报、跳点或召回。
- 上游 `/robot_task/send_point` 仍把有效完整路线一次性交给 SDK，不改原有多点导航语义。

## 任务抢占与生命周期

- 等待期间收到有效 `/robot_task/send_point` 时，取消当前等待和未完成的到位请求，执行上游新路线；旧超时和迟到回调不能推进旧路线。
- `/robot_task/send_point` 会先完成 JSON、非空路线和非空节点校验；无效请求不会抢占当前有效屏幕任务。
- `/robot_task/send_stop`、手动新出发、手动回充、巡仓、召回会取消当前屏幕等待。
- Activity 销毁时停止 `9088` 和现有 `9095` HTTP 服务，并取消等待、到位请求和相关线程资源。
- 原屏幕单点到达后等待 20 秒再追加固定“出餐口”的逻辑已移除，由本流程统一处理。

## 已知限制

`/pickup_status` 按上游现有协议不包含仓位号、点位名称或任务 ID，因此 App 只能把有效回调关联到“当前正在等待的点位”。代次隔离可阻止已取消任务的本地超时继续执行，但协议本身无法识别跨点位迟到且恰好落入下一等待阶段的回调，现场联调时需要关注上游回调时序。
